# MF01 v2.0 — FE Specification
## Pre-Mission Feasibility & Resource Readiness

## 1. Version History

| Version | Change |
|---|---|
| v1.x | Previous frontend flow focused mainly on drone/pre-flight preparation. |
| **v2.0** | Refactored MF01 into **Pre-Mission Feasibility & Resource Readiness**. FE now covers proposed inspection scope/site feasibility, personnel readiness, UAV availability, drone technical inspection, and overall readiness before mission creation. |

## 2. FE Goal

MF01 must answer one question before the user can proceed to mission creation:

> Is the proposed inspection operation feasible, and are the required personnel and UAV resources ready?

MF01 **does not create an InspectionMission**. It creates/reviews a `PreMissionAssessment` and hands a READY assessment to MF02.

## 3. Primary Actors

- Mission Manager: creates and reviews the assessment.
- Drone Technician / Technical Drone Team: performs UAV technical inspection when required.
- Backend: authoritative source for scope, feasibility, availability, technical health and assessment status.

## 4. Main User Flow

```text
Assessment List / Create Assessment
        ↓
Define Proposed Scope + Planned Window
        ↓
Review Site / Operational Feasibility
        ↓
Review Personnel Candidates
        ↓
Review UAV Candidates
        ↓
Technical Inspection if required
        ↓
Overall Readiness Evaluation
        ↓
READY ───────────────→ Proceed to MF02
NOT_READY/INCOMPLETE → Resolve issue / Re-evaluate
```

Do not ask the Manager to create a mission in this flow.

## 5. Required Screens

### 5.1 Pre-Mission Assessment List

Use the global enterprise table pattern.

Columns:
- Assessment ID
- Region / Line
- Planned Window
- Site Feasibility
- Personnel Readiness
- Drone Readiness
- Overall Status
- Valid Until
- Created By
- Updated At
- Actions

Filters:
- Region
- Line
- Status
- Planned Date
- Creator

Actions:
- Create Assessment
- Open
- Re-evaluate where permitted
- Cancel where permitted

### 5.2 Create / Edit Assessment

Sections:
1. Proposed Inspection Scope
2. Planned Time Window
3. Optional GIS operation area
4. Assessment summary

Scope selection follows project hierarchy:
`Region → Line / Line Segment → Tower / Asset`.

GIS may assist asset selection, but backend authorization remains authoritative.

Validation:
- required Region/scope;
- at least one inspection target;
- end > start;
- no obsolete planned window;
- invalid GIS geometry cannot be submitted;
- out-of-scope assets cannot be retained.

### 5.3 Assessment Workspace

Recommended layout:

```text
┌───────────────────────────────────────────────────────────┐
│ Assessment #...     Status: READY/NOT_READY   Valid Until │
├───────────────────────────────────────────────────────────┤
│ Scope Summary │ Site │ Personnel │ UAV │ Technical Detail │
├───────────────────────────────────────────────────────────┤
│ Main workspace                                            │
│                                                           │
├───────────────────────────────────────────────────────────┤
│ Overall Readiness                                        │
│ Site       ✓ FEASIBLE                                    │
│ Personnel  ✓ AVAILABLE                                   │
│ UAV        ✓ ELIGIBLE                                    │
│ Technical  ✓ PASSED                                      │
│                                   [Re-evaluate] [MF02 →]  │
└───────────────────────────────────────────────────────────┘
```

### 5.4 Site Feasibility

Display only checks actually supported by backend/project data.

Show:
- proposed scope;
- GIS area/map;
- configured operational constraints;
- check result;
- warning/failure reason;
- last evaluated time.

States:
- FEASIBLE
- NOT_FEASIBLE
- INCOMPLETE

Do not claim realtime weather/airspace/legal validation unless an actual integration exists.

### 5.5 Personnel Readiness

Table:
- Name
- Operational Role
- Region
- Availability
- Eligibility
- Conflict
- Reason

MF01 shows **candidates**, not final MissionAssignment.

Do not let frontend infer availability from local data. Backend result is authoritative.

### 5.6 UAV Readiness

Table:
- UAV Code/Name
- Operational Status
- Technical Health
- Last Inspection
- Valid Until
- Eligibility
- Action

Semantic distinction:
- Operational Status: AVAILABLE / RESERVED / IN_USE / MAINTENANCE / UNAVAILABLE / LOST
- Technical Health: UNKNOWN / HEALTHY / WARNING / CRITICAL
- Mission eligibility: computed backend policy result.

Never collapse these into one generic `status`.

### 5.7 Drone Technical Inspection

This is an operational/technical dashboard, not a generic form.

```text
Drone Technical Inspection
────────────────────────────────────────
Connection        ● Connected
FC Target          ...
Firmware           ...
Inspection Source  CLI / MSP / Telemetry
Valid Until        ...

Flight Controller  ✓ Healthy
Sensors            ✓ Healthy
Battery / Power    ⚠ Warning
Motor / ESC        ✓ Healthy
Communication      ✓ Healthy
Safety / Failsafe  ✓ Passed

Technical Health   WARNING
Eligibility        NOT ELIGIBLE / ELIGIBLE

[View Metrics] [Run/Re-run Inspection]
```

Technical metric table:
- Subsystem
- Metric
- Value
- Unit
- Required
- Severity
- Pass/Fail

The FE must not hardcode readiness thresholds. Display backend evaluation.

Do not expose device secrets or raw access credentials.

### 5.8 Overall Readiness

Display all mandatory groups and failure reasons.

Only backend can return `READY`.

When READY:
- show `Valid Until`;
- enable **Proceed to Create Mission**;
- navigate to MF02 with `assessmentId`.

When NOT_READY/INCOMPLETE:
- disable proceed action;
- show exact failed conditions;
- provide contextual actions such as re-run technical inspection or re-evaluate.

## 6. State Handling

Assessment:
`DRAFT → EVALUATING → READY | NOT_READY | INCOMPLETE → EXPIRED/CONSUMED/CANCELLED`

UI rules:
- READY but expired is never presented as actionable READY.
- CONSUMED assessment links to its created mission.
- EVALUATING shows progress/loading and prevents duplicate evaluation.
- stale update / HTTP 409 prompts refresh, never silently overwrites.

## 7. API Integration Rules

Expected integration surface:

```text
POST /api/v2/pre-mission-assessments
GET  /api/v2/pre-mission-assessments/{id}
POST /api/v2/pre-mission-assessments/{id}/evaluate
POST /api/v2/pre-mission-assessments/{id}/re-evaluate
GET  /api/v2/pre-mission-assessments/{id}/personnel-candidates
GET  /api/v2/pre-mission-assessments/{id}/drone-candidates

POST /api/v2/drones/{droneId}/technical-inspections
GET  /api/v2/drones/{droneId}/technical-inspections/latest
```

Use actual backend contract if names differ.

FE must:
- handle cancellation;
- prevent accidental double-submit;
- display backend `errorCode`;
- refetch after mutations;
- never send client-calculated READY/health as authority.

## 8. Loading / Empty / Error States

Every data surface must have:
- loading state;
- empty state;
- permission denied state;
- server/network error;
- stale/concurrent update;
- expired assessment;
- integration timeout where applicable.

Avoid blank tables with no explanation.

## 9. Permissions

Hide/disable actions for UX, but do not treat hiding as authorization.

Examples:
- Manager can create/evaluate assessment within scope.
- Technical Team can execute technical inspection when authorized.
- Read-only users receive view-only UI.

## 10. Responsive / Accessibility

- Desktop-first operational UI.
- Tables horizontally scroll on narrow screens.
- Keyboard-accessible actions.
- Visible focus states.
- Status must use icon/text in addition to color.
- Form inputs have labels and validation messages.
- Confirm destructive/state-changing actions.

## 11. FE Acceptance Criteria

- MF01 creates no mission.
- proposed scope/time is persisted through assessment.
- site/personnel/UAV readiness are visually distinct.
- technical health and operational status are not conflated.
- technical inspection supports metric-level detail.
- READY expiry is visible.
- Proceed to MF02 works only with valid READY assessment.
- 409/stale states are recoverable.
- no unsupported realtime feasibility claim is shown.
- all primary screens follow the shared UAV-PMS design system.
