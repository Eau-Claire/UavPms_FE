# MF02 v2.0 — FE Specification
## Create & Assign Inspection Mission

## 1. Version History

| Version | Change |
|---|---|
| v1.0.x | Create Mission flow independently selected Region, Line, Towers/Assets, UAV and Inspector. |
| **v2.0** | Renumbered/refactored to MF02. The FE now **consumes a READY Pre-MissionAssessment from MF01**, reviews its scope, selects final eligible personnel/UAV, performs final backend revalidation, creates the mission and supports Inspector Accept/Postpone. |

## 2. FE Goal

MF02 converts a valid READY assessment into an actual inspection mission.

MF02 must not repeat the entire MF01 workflow.

Key rule:

> Load → review → confirm → select final resources → create.

Do **not** force the Manager to re-select Region/Line/Towers from zero when the assessment already contains the evaluated scope.

## 3. Primary Actors

- Mission Manager
- Inspector / Pilot
- Backend
- Notification subsystem

## 4. Main User Flow

```text
Open READY Assessment
        ↓
Review Scope + Planned Window
        ↓
Confirm Mission Assets
        ↓
Select Eligible Inspector / Pilot
        ↓
Select Eligible READY UAV
        ↓
Enter / Confirm Mission Information
        ↓
Final Backend Revalidation
        ↓
Create Mission
        ↓
Notification
        ↓
Inspector Review
   ├── Accept
   └── Postpone + reason
```

## 5. Entry Conditions

MF02 receives an `assessmentId`.

Before rendering an actionable create page:
- assessment exists;
- status = READY;
- not expired;
- not already consumed;
- current user has create permission.

If invalid, show a dedicated state and do not render a misleading active Create button.

## 6. Required Screens

### 6.1 Create Mission from Assessment

Recommended page structure:

```text
┌────────────────────────────────────────────────────────────┐
│ Create Inspection Mission       Assessment #...   READY    │
├────────────────────────────────────────────────────────────┤
│ Scope Summary                                               │
│ Region → Line → 12 Towers                    [View on GIS]  │
├────────────────────────────────────────────────────────────┤
│ Mission Information                                        │
│ Name | Planned Start | Planned End | Priority | Notes       │
├────────────────────────────────────────────────────────────┤
│ Personnel                                                   │
│ ○ Inspector A  AVAILABLE                                    │
│ ● Inspector B  AVAILABLE                                    │
├────────────────────────────────────────────────────────────┤
│ UAV                                                         │
│ ● UAV-03  AVAILABLE | HEALTHY | inspection valid            │
│ ○ UAV-07  AVAILABLE | WARNING | policy result ...           │
├────────────────────────────────────────────────────────────┤
│                                     [Cancel] [Create Mission]│
└────────────────────────────────────────────────────────────┘
```

### 6.2 Scope Review

Show:
- Region
- Line / Line Segment
- Towers / Assets
- count
- optional assessment geometry
- GIS preview

Scope is initially read from MF01.

If product allows material scope edits:
- clearly warn that changes may invalidate readiness;
- backend decides whether `REASSESSMENT_REQUIRED`;
- never silently expand scope.

### 6.3 Mission Information

Fields:
- Mission Name
- Description / Notes
- Planned Start
- Planned End
- Priority
- Mission Type where applicable

Validation:
- required name;
- end > start;
- at least one MissionAsset;
- server validation messages displayed next to relevant field.

### 6.4 Personnel Assignment

Only display candidates allowed by backend.

Columns/card details:
- Name
- Role
- Region
- Current Availability
- Eligibility
- Schedule Conflict
- Required/Optional role if supported

Selection must support actual project assignment policy.

If multiple required assignments exist, each assignment has its own response status.

### 6.5 UAV Assignment

Display:
- UAV
- Operational Status
- Technical Health
- Technical Inspection validity
- Current conflict
- eligibility

Do not run Betaflight/FC technical inspection here.

MF02 only revalidates current technical/operational state through backend.

### 6.6 Final Review

Before create, show compact summary:
- assessment reference;
- scope;
- schedule;
- personnel;
- UAV;
- warnings.

Create button:
- disabled during submit;
- protected from double click;
- uses idempotency behavior supported by backend.

### 6.7 Creation Result

After successful create:
- route to Mission Detail;
- show mission ID/status;
- show assignment summary;
- show notification delivery as secondary state, not mission creation authority.

Do not show mission creation failed merely because asynchronous notification delivery is pending/failed.

### 6.8 Inspector Mission Review

Assigned Inspector/Pilot sees:
- mission summary;
- GIS/scope;
- schedule;
- assigned role;
- assigned UAV;
- notes;
- latest version/update time.

Actions:
- **Accept Mission**
- **Postpone Mission**

No normal-flow Reject action.

### 6.9 Postpone Dialog

Required:
- reason text;
- optional structured reason code if backend supports it.

Rules:
- blank/whitespace reason invalid;
- confirm before submit;
- display updated assignment status after success.

## 7. State Model

Mission:
`DRAFT/PENDING_ACCEPTANCE → ASSIGNED/ACCEPTED | POSTPONED | CANCELLED`

Assignment:
`PENDING → ACCEPTED | POSTPONED | REPLACED | CANCELLED`

UI must not infer mission acceptance from one user when multiple required assignments exist. Render backend aggregate status.

## 8. Final Revalidation UX

MF01 readiness is a snapshot. MF02 can fail at commit because resources changed.

Handle explicit backend conflicts:

- `ASSESSMENT_EXPIRED`
- `ASSESSMENT_ALREADY_CONSUMED`
- `REASSESSMENT_REQUIRED`
- `PERSONNEL_UNAVAILABLE`
- `RESOURCE_SCHEDULE_CONFLICT`
- `DRONE_UNAVAILABLE`
- `DRONE_INSPECTION_EXPIRED`
- `DRONE_NOT_ELIGIBLE`
- `CONCURRENT_UPDATE`

UX response:
- explain the exact resource/problem;
- preserve safe user-entered mission metadata;
- refresh candidate/resource state;
- redirect to MF01 only when reassessment is actually required.

## 9. API Integration Rules

Expected surface:

```text
POST /api/v2/missions
GET  /api/v2/missions/{missionId}
PATCH /api/v2/missions/{missionId}

POST /api/v2/missions/{missionId}/assignments/{assignmentId}/accept
POST /api/v2/missions/{missionId}/assignments/{assignmentId}/postpone

GET /api/v2/pre-mission-assessments/{assessmentId}/create-mission-context
```

Create request references `assessmentId`.

FE must not trust cached candidate state as current authority. Backend performs final validation.

## 10. Concurrency / Idempotency

- Disable Create while request is active.
- Preserve idempotency key for retry of the same create attempt.
- HTTP 409 never triggers blind automatic resubmit.
- On stale mission during Inspector review, refresh latest mission before response.
- Show “mission updated” state if Manager changed data after page load.

## 11. Notifications

Notification UI can show:
- pending;
- sent;
- failed/retrying where exposed.

Notification failure is not equivalent to mission creation failure.

## 12. Permissions

- only authorized Manager sees create/edit actions;
- Inspector can respond only to own assignment;
- mission-scoped access controls assets visible to assigned Inspector;
- frontend visibility is convenience only; backend remains authoritative.

## 13. Loading / Empty / Error States

Required:
- loading assessment context;
- assessment unavailable/expired/consumed;
- no eligible personnel;
- no eligible UAV;
- resource changed;
- validation error;
- 403;
- 409;
- 5xx/network failure.

## 14. FE Acceptance Criteria

- MF02 requires READY assessment.
- scope is loaded from MF01 rather than redundantly rebuilt.
- resource current state is visible.
- technical inspection is not duplicated in MF02.
- Create is protected against double-submit.
- resource conflicts produce actionable UX.
- mission creation success is independent of notification delivery.
- Inspector has Accept/Postpone only.
- Postpone requires reason.
- field check-in is absent from MF02 and remains MF03.
- UI follows shared UAV-PMS design system.
